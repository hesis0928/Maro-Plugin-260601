# Maya 내부 ROS 2 축·노드 기반 로봇화 플러그인 — 설계 (S1+S2 수직 슬라이스)

작성일: 2026-08-13
상태: 승인 대기

## 1. 목적

Maya에서 모델링된 오브젝트에 사용자가 직접 축과 능력 노드를 배치·배선하여 "로봇화"하고, 그 로봇을 Maya 뷰포트 안에서 ROS 2와 양방향으로 연동해 구동한다. 사용자는 **Maya만 열면 되며**, 별도 터미널이나 외부 프로그램을 띄우지 않는다.

기존 ROS 2 시뮬레이터(Gazebo, CARLA) 대비 차별점은 Maya의 리깅·디포머 체계와 DG(Dependency Graph)를 그대로 활용한다는 점이다. 이 슬라이스는 그중 리깅(①)과 노드 기반 아키텍처(③)의 기반을 만든다.

## 2. 범위

전체 구상은 5개 서브시스템으로 분해되며, 각각 별도의 스펙 → 플랜 → 구현 사이클을 갖는다.

| # | 서브시스템 | 이 스펙 |
|---|---|---|
| S1 | 로봇 정의 코어 (축·능력 노드·연결) | **포함** |
| S2 | ROS 2 런타임 브릿지 (상태 발행 / 명령 수신) | **포함 (최소)** |
| S3 | 커스텀 노드 그래프 에디터 UI | 제외 |
| S4 | 센서·합성 데이터 (카메라/LiDAR → sensor_msgs) | 제외 |
| S5 | 파이프라인 통합 (URDF/USD 상호운용) | 제외 |

### 이번 슬라이스에 포함

- 커스텀 Maya DG 노드 타입 (축, 능력 노드, 로봇 루트)
- 뷰포트에서 축을 오브젝트에 배치(포인팅)하고 축끼리 연결
- 좌표계·스케일·회전 표기 양방향 변환 라이브러리
- ROS 2 네이티브 연동: `/joint_states` · `/tf` 발행, `/joint_commands` 구독
- 사용자 기준 축 보정(데이터 모델 + 커맨드)
- 3단계 통합 검증

### 명시적 제외

- 물리 시뮬레이션(중력·충돌·다이내믹스). 이 슬라이스는 **기구학적 구동**만 다룬다.
- 커스텀 Qt 노드 에디터 UI. v1은 Maya 기본 Node Editor를 사용한다.
- 코드 작성 기반 오써링(rclpy 콘솔, C++ 플러그인). 오써링은 **배선 + 속성 입력**만으로 이루어진다.
- URDF/USD 익스포트
- 센서 데이터 스트리밍 (기존 Track B 코드는 이번 슬라이스에서 건드리지 않음)
- 기존 TCP/UDP 네트워크 격리 구조 — **폐기 확정.** 네이티브 `rclcpp` 직접 링크로 대체한다.

## 3. 핵심 개념

### 축 (Axis)

Maya 오브젝트 **하나**에 바인딩되는 앵커. 사용자가 뷰포트에서 위치를 지정한다. 그 오브젝트의 움직임을 전담한다.

로봇 외관은 움직이는 부위별로 **여러 오브젝트를 합쳐** 모델링하는 것을 전제로 한다.

### 능력 노드 (Capability Node)

축에 **여러 개 쌓이는 모듈**. 어떤 노드를 쌓았는지에 따라 그 축의 성격이 **결정되는 것이 아니라 창발**한다. 타입을 미리 고르지 않는다.

- 회전 노드를 쌓으면 회전 관절이 된다
- 회전 노드 + X/Y/Z 리밋 노드를 쌓으면 제한된 회전 관절이 된다
- 센서 방향 노드 + 감지 반경 노드를 쌓으면 센서가 된다
- 센서 축에 회전 노드를 추가로 쌓으면 **움직이는 센서**가 된다

### 2계층 그래프

- 축 ↔ 축: 기구학 체인 (부모-자식)
- 축 ↔ 능력 노드: 능력 스택

## 4. 아키텍처

### 상태 소유 원칙

**진실의 원천은 Maya DG 단 하나.** 축·능력 노드·연결·파라미터는 전부 커스텀 DG 노드의 어트리뷰트로만 존재하며, 그 밖 어디에도 사본을 두지 않는다.

- 향후 커스텀 에디터(S3)는 **자체 상태가 없는 순수 뷰**다. 읽을 때 DG에서 읽고, 쓸 때 `MPxCommand`를 경유한다.
- ROS 2 런타임도 상태를 소유하지 않는다. DG에서 읽고 DG에 쓴다.

상태가 하나뿐이면 동기화가 깨질 대상 자체가 존재하지 않는다.

### 바인딩은 message 어트리뷰트로

축이 담당 오브젝트를 가리킬 때 이름 문자열이 아니라 **message 커넥션**으로 연결한다. 이름으로 들면 rename·삭제 시 깨지지만, message 연결은 Maya가 rename·delete·undo를 자동 추적한다. 축↔축, 축↔능력 노드 연결도 전부 실제 DG 커넥션으로 맺는다.

### DG 노드 타입

**`maroAxis`** — `MPxLocatorNode` 상속. 뷰포트에 축 기즈모로 그려지며 직접 클릭·조작 가능.

| 어트리뷰트 | 타입 | 역할 |
|---|---|---|
| `targetObject` | message | 전담하는 Maya 오브젝트 하나 |
| `parentAxis` | message | 상위 축 (기구학 계층) |
| `jointName` | string | ROS 2에 노출될 관절 이름 |
| `capabilityIn[]` | array | 능력 노드 스택 입구 |
| `axisConvention` | enum(X/Y/Z) + bool | 사용자 기준 축 보정 — 어느 로컬 축이 회전축인지 + 부호 반전 여부 (§7) |
| `outValue` | double | 계산된 관절 구동값 (스칼라). `joint_states`에 실리는 값 |
| `outTransform` | matrix | 계산 결과 프레임. `/tf` 발행 및 Maya 어트리뷰트 연결용 |
| `enabled` | bool | 비활성 상태 표시 |

`outValue`는 Maya의 **임의 어트리뷰트에 연결 가능**하다. 관절 회전, 카메라 초점, 파티클 에미터 등 어디에나 꽂을 수 있으며, 이것이 차별점 ③이 실현되는 지점이다.

**능력 노드** — 전부 `MPxNode` 상속. 공통 출력 `capabilityOut` → 축의 `capabilityIn[i]`.

| 노드 | 주요 어트리뷰트 |
|---|---|
| `maroRotation` | `axisVector`, `angle` |
| `maroLimit` | `enableX/Y/Z`, `minX/maxX`, `minY/maxY`, `minZ/maxZ` |
| `maroSensorDirection` | `direction` |
| `maroSensorRange` | `range`, `coneAngle` |

**`maroRobot`** — 축들을 묶어 하나의 ROS 2 발행 단위로 만드는 루트. `robotName`, `enabled`.

### 스택 합성 규칙

축의 `capabilityIn` 배열을 **인덱스 순서대로 평가**한다. `maroRotation`이 기본값을 생성하고, 뒤따르는 `maroLimit`들이 순차적으로 클램프한다. 여러 리밋 노드를 쌓으면 합성되어 유연한 회전 반경이 만들어진다.

Maya 디포머 스택과 동일한 멘탈 모델이므로 Maya 사용자에게 별도 설명이 필요 없다.

## 5. 좌표 변환 라이브러리 (`MaroTransform`)

Maya API와 rclcpp **어느 쪽에도 의존하지 않는 순수 함수 라이브러리**로 분리한다. 좌표 변환 버그는 육안으로 잡히지 않고 "뭔가 이상하다"로만 나타나므로, Maya 없이 실행되는 테스트로 못박아야 한다.

### 변환 대상

1. **좌표계 기저** — Maya(Y-up, 우수좌표계) ↔ ROS REP-103(Z-up, X-forward, Y-left, 우수좌표계). 기저 변환 행렬로 처리.
2. **스케일** — Maya 씬 단위 ↔ ROS 미터. 하드코딩하지 않고 `MDistance`에서 현재 씬 단위를 읽어 **주입**한다. Maya 기본은 cm이나 사용자가 변경할 수 있으며, 이를 놓치면 로봇이 100배 크기로 나타난다.
3. **회전 표기** — Maya 오일러(노드별 `rotateOrder` 상이) + `MQuaternion` ↔ `geometry_msgs/Quaternion`. 축별 `rotateOrder`를 읽어 반영한다.

### API 형태

`rosToMaya()` / `mayaToRos()` 양방향 대칭. 씬 단위와 축 보정값(`axisConvention`)은 **입력 파라미터로 받는다** — 라이브러리 내부에 상태를 두지 않기 위함이며, 이 덕분에 보정된 케이스도 동일한 자동 테스트로 검증된다.

> **중요**: 씬 단위(`MDistance`)와 `axisConvention`은 Maya API·DG 접근이 필요하므로 **반드시 메인 스레드에서 읽어** 큐에 함께 실어 보낸다. 백그라운드 스레드는 전달받은 값만 사용하며 Maya를 조회하지 않는다(§6 불변 규칙).

### 핵심 불변식

```
mayaToRos(rosToMaya(x)) ≈ x   (부동소수 허용오차 내)
```

랜덤 값을 대량 생성해 이 불변식을 깨는 입력을 탐색한다. 짐벌락 근처, 극단 스케일, 음수 각도가 여기서 검출된다.

## 6. 런타임과 스레딩

Maya API는 스레드 안전하지 않고 rclcpp는 자체 executor 스레드를 사용한다. 잘못 엮으면 재현 불가능한 타이밍에 Maya가 죽는다.

> **불변 규칙: ROS 2 스레드에서 Maya API를 절대 호출하지 않는다.**

### 스레드 역할 분담

| | Maya 메인 스레드 | 백그라운드 스레드 |
|---|---|---|
| 발행 | 어트리뷰트 **생값** + 씬 단위 + `axisConvention`을 읽어 큐에 적재 | 좌표 변환 → publish |
| 수신 | 큐에서 **Maya 좌표값**을 꺼내 DG에 기록 | subscribe → 좌표 변환 |

변환에 필요한 컨텍스트(씬 단위, 축 보정값)는 Maya 조회가 필요하므로 메인 스레드가 큐에 함께 실어 보낸다. 백그라운드 스레드는 Maya를 일절 조회하지 않는다.

**좌표 변환은 백그라운드 스레드에서 수행한다.** 순수 계산 자체는 Maya를 크래시시킬 수 없으나, 변환 코드에 결함이 생겨 루프가 발생하면 메인 스레드가 멈춰 사용자에게는 크래시와 구분되지 않는 프리즈로 나타난다. 백그라운드로 옮기면 이 위험이 제거되고, 메인 스레드 부하가 줄어 뷰포트 응답성도 개선된다.

**두 개의 큐가 유일한 접점**이며 그 외 공유 상태는 없다.

메인 스레드 진입점은 `MTimerMessage` 콜백이다. 기존 `rosSimCmd.cpp`에서 검증된 패턴을 재사용한다.

### 프로세스 분리를 채택하지 않는 이유

변환을 별도 프로세스로 분리하면 매 프레임 IPC 왕복 지연이 발생한다. 이는 폐기하기로 한 기존 TCP/UDP 구조와 동일하며, "Maya만 열면 된다"는 요구와도 충돌한다. 스레드 분리로 프리즈 위험은 동일하게 제거된다.

### 생명주기

- `initializePlugin`: `rclcpp::init` → 노드 생성 → executor 스레드 시작
- `uninitializePlugin`: 역순 정지

Maya를 켜둔 채 플러그인만 언로드·리로드해도 좀비 스레드나 잔여 컨텍스트가 남지 않아야 한다.

DLL 의존성은 검증된 PostBuildEvent(ROS 2 런타임 DLL을 출력 폴더로 복사) 방식을 사용한다.

## 7. 토픽 계약

| 방향 | 토픽 | 타입 |
|---|---|---|
| 발행 | `/<robotName>/joint_states` | `sensor_msgs/JointState` |
| 발행 | `/tf` | `tf2_msgs/TFMessage` |
| 구독 | `/<robotName>/joint_commands` | `sensor_msgs/JointState` |

`/tf`를 v1에 포함하는 이유: **RViz2의 TF 디스플레이는 URDF 없이 동작한다.** 축 프레임이 RViz2에 그대로 표시되므로, URDF 익스포트(S5) 없이도 좌표 변환의 정확성을 시각적으로 확인할 수 있다.

### 사용자 기준 축 보정

3단계 시각 확인에서 축 방향이 뒤집힌 것이 발견되면, 사용자가 의도한 기준 축을 선택하고 그에 맞춰 변환을 재계산한다.

`maroAxis`의 `axisConvention` 어트리뷰트(어느 로컬 축이 회전축인지 + 부호)에 저장되며, 변환 라이브러리는 이를 입력 파라미터로 받는다. 보정값은 축마다 개별 저장되고 씬에 함께 저장된다.

v1 범위는 **데이터 모델 + 설정 커맨드**까지다. 후보를 시각적으로 미리보며 선택하는 피커 UI는 S3로 이관한다.

## 8. 삭제 규칙

### 비대칭 연쇄 삭제

- **오브젝트 삭제 → 바인딩된 축도 삭제.** 축은 오브젝트에 종속된 부착물이다.
- **축 삭제 → 오브젝트는 생존.**

삭제 전파는 반드시 사용자의 삭제와 **같은 undo 청크**에 묶인다. 그렇지 않으면 Ctrl+Z 시 오브젝트만 복원되고 축은 복원되지 않아 상태가 어긋난다.

### 고아 능력 노드

축이 삭제되어도 능력 노드는 **삭제되지 않고 씬에 남아 재사용 가능**하다. 다음 규칙으로 부작용을 통제한다.

- **평가되지 않음** — 축에 연결되지 않은 능력 노드는 런타임에서 완전히 무시된다. 실행 비용도 크래시 경로도 없다.
- **`maroOrphanSet`에 자동 등록** — 축에서 분리되는 즉시 전용 objectSet에 담긴다. 두 가지 목적이 있다.
  1. 사용자가 재사용할 노드를 한 곳에서 찾을 수 있다.
  2. `File > Optimize Scene Size`가 미연결 DG 노드를 삭제하는 것을 방지한다. 세트에 속하면 연결이 존재하므로 살아남는다. 이 장치가 없으면 씬 정리 한 번으로 설정값이 소실된다.
- **재연결 시 동일 검증** — 고아를 다른 축에 연결할 때도 §9 원칙 2의 구성 시점 검증을 통과해야 한다.

## 9. 견고성 설계 원칙

Maya 플러그인의 크래시는 Maya 세션 전체를 종료시키고 사용자의 미저장 작업을 소실시킨다. "튕기지 않는다"를 기능이 아닌 **설계 제약**으로 둔다.

### 원칙 1 — 예외는 경계를 넘지 않는다

`compute()`, 타이머 콜백, DG 메시지 콜백, ROS 2 구독 콜백 전부 최상위에 catch-all을 두고, 로그를 남긴 뒤 안전한 기본값으로 복귀한다. ROS 2 스레드에서 예외가 새면 스레드만 조용히 종료되어 "무반응" 상태가 되는데, 이는 크래시보다 진단이 어렵다.

### 원칙 2 — 불가능한 상태는 구성 시점에 차단

평가 시점에 실패하게 두지 않고 **연결 시점에 거부**한다.

- 순환 연결(축 A→B→A) 탐지 및 거부
- `hasFn(MFn::kTransform)` 검사 실패 시 축 바인딩 거부
- 이미 축이 바인딩된 오브젝트에 추가 바인딩 거부 (**"축 하나 = 오브젝트 하나"** 불변식 강제)

거부 시 반드시 사유를 스크립트 에디터에 출력한다. 조용한 실패를 금지한다.

### 원칙 3 — 실패는 크래시도 무시도 아닌 비활성화

삭제 이외의 사유로 축이 유효하지 않게 되면 **해당 축만 비활성 상태로 전환**하고, 뷰포트에 경고 색으로 표시하며 사유를 출력한다. 로봇의 나머지 축은 계속 동작한다. 부분 실패가 전체를 멈추지 않는다.

(오브젝트 삭제로 인한 경우는 §8에 따라 비활성화가 아니라 삭제된다.)

### 원칙 4 — 경계에서 전부 검증, NaN은 Maya에 유입되지 않는다

`NaN`/`inf`가 Maya 어트리뷰트에 유입되면 내부 상태가 손상되어 이후 임의 지점에서 죽는다. Maya로 나가는 모든 값에 유한성 검사를 적용하고, 실패 시 직전 유효값을 유지한다. ROS 2 수신 메시지도 이름 매칭·배열 길이·값 범위 검증을 통과해야 반영한다.

### 원칙 5 — Maya API 규칙 준수

- 스레드 격리 (§6)
- **`compute()` 내에서 씬 그래프 수정 금지.** Maya가 죽는 전형적 원인이다. compute는 순수 계산만 수행한다.
- **어트리뷰트 쓰기는 `MPxCommand` 경유.** Undo 스택 정합성이 유지된다.

### 원칙 6 — 자원 수명과 큐 상한

- 콜백 ID를 RAII로 관리하여 언로드 시 확실히 해제한다. 댕글링 콜백은 즉시 크래시로 이어진다.
- 수신 큐에 상한을 두고 초과 시 오래된 명령부터 폐기한다. 실시간 제어에서 의미 있는 것은 최신 명령이며, 상한이 없으면 ROS 2가 Maya보다 빠를 때 메모리가 고갈된다.

## 10. 검증 전략

세 방법을 하나의 절차로 결합한다. 아래로 갈수록 느리고 비싸므로, 상위 단계에서 검출되면 하위로 진행하지 않는다.

### 1단계 — 자동 왕복 테스트 (Maya 불필요, 수 초)

`MaroTransform` 단위 테스트 + 왕복 불변식 `mayaToRos(rosToMaya(x)) ≈ x`를 랜덤 값 대량으로 검증. 짐벌락 근처·극단 스케일·음수 각도가 여기서 검출된다. 좌표 버그의 대부분을 이 단계에서 잡는다.

### 2단계 — 자동 계약 테스트 (Maya 배치 모드)

`mayapy`로 GUI 없이 Maya를 기동해 축·능력 노드를 스크립트로 구성하고 다음을 자동 검증한다.

- `ros2 topic echo` 수신값이 기대값과 일치하는가
- `ros2 topic pub`로 명령 주입 시 DG 어트리뷰트가 기대대로 변경되는가
- **견고성 시나리오**: 오브젝트 삭제, 순환 연결 시도, 타입 불일치 바인딩, NaN 주입 시 크래시 없이 거부·비활성화·연쇄 삭제가 규칙대로 동작하는가

견고성을 자동 테스트로 고정하는 것이 이 단계의 핵심이다. "튕기지 않는다"는 수동으로 매번 확인할 수 없으므로 회귀를 테스트로 막는다.

### 3단계 — 시각 확인 (최종)

Maya 뷰포트와 RViz2의 TF 디스플레이를 나란히 놓고 동일하게 움직이는지 확인한다. 1·2단계가 숫자로 검출하지 못하는 "축 방향 반전" 등을 여기서 발견하며, 발견 시 §7의 축 보정으로 수정한다.

## 11. 향후 서브시스템과의 관계

- **S3 (에디터 UI)**: 본 설계의 DG 데이터를 그대로 소비하는 순수 뷰로 구현한다. 상태를 복제하지 않는다.
- **S4 (센서·합성 데이터)**: 기존 Track B(`ViewportStreamer`) 코드를 본 설계의 축·센서 노드 체계에 연결한다.
- **S5 (파이프라인)**: 축 체인과 능력 노드 스택으로부터 URDF를 생성한다. 본 설계의 데이터 모델이 URDF 생성에 필요한 정보를 담고 있어야 한다.
